## Verified semantics vs local evidence

- [Supabase official S3 Authentication](https://supabase.com/docs/guides/storage/s3/authentication): Dashboard-generated long-lived S3 access key pairs bypass RLS and give broad operations on all buckets. **These are not the same credentials as an end-user JWT.** The documented S3 Session Token mechanism accepts valid user JWT and respects Storage RLS.
- [Supabase Storage Access Control](https://supabase.com/docs/guides/storage/security/access-control): a service key in the Storage Authorization header bypasses RLS. A Storage policy cannot constrain a principal that bypasses it.
- [Supabase public buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals): anonymous possession of a public object URL permits reading, including historical cached URLs. Even immediate code changes cannot revoke previously copied bytes.
- [Supabase S3 Compatibility](https://supabase.com/docs/guides/storage/s3/compatibility): operations through S3 and REST are interoperable; S3 versioning is not provided. Storage metadata and backend bytes are distinct concerns.
- **Observed LOCAL only, prior #153 fixed HEAD:** a service-role JWT used as a locally signed S3 Session Token can PUT synthetic WAV bytes into a synthetic public bucket even when the object has an opaque key and text/plain MIME; anonymous GET reads identical bytes. This demonstrates a local bypass of in-process media preflight/prefix/Content-Type checks and RLS. This is **not** a live leak claim or a direct test of a Dashboard-issued access key pair.
- **NEW test:** compare a real signed-in synthetic GoTrue user JWT used as S3 Session Token against the local privileged service JWT on exactly the same public-bucket key. The valid ordinary user must receive 4xx, with no object created; the privileged control succeeds and is anonymously readable. If either protocol case is unavailable, fail the test rather than label it safe. Actual service keys/S3 key pairs from hosted accounts are never read.

## Recommended containment architecture (design ONLY, not executed)

1. **Account/credential mapping, separately authorized READ-ONLY:** enumerate *metadata* (not secret values) of project S3 connections and access-key count/ownership/last use where the provider exposes it; Vercel server-only secret references and environment scopes (Production/Preview/Development); deployment SHA, Cron, ETL, batch, CLI, local backups, service-role destinations, public legacy buckets and all public URL derivations. Locate actual S3 key holders and automatic uploads before changing a key or bucket. Treat unknown external holders as blockers. Do not copy access keys into GitHub or ChatGPT logs.
2. **Disallow unrestricted S3 credentials for routine media publishing:** require verified server identity with least-privileged per-user JWT/session subject to **correct** Storage RLS for uploads, and/or a dedicated audited credential broker restricted at the actual network/Storage gateway (with provider-supported isolation). Do not infer Dashboard S3 keys are bucket-scoped. Ensure only the broker can reach unrestricted credentials and that no alternate direct S3/REST/SDK route is available. A server-side TypeScript check or DB trigger is not sufficient while a privileged key can call S3 directly.
3. **Private-only custody first:** use a guaranteed PRIVATE staging/destination with immutable byte provenance, SHA256/decoder verification, versioned unique keys and no ambiguous-overwrite deletion. Commit only a private pointer with DB-locked fresh ownership/session/rights/R18/publication/AI-vs-Human authority and unique nonce, fail on conflict/replay and handle crash/recovery without PUBLIC copy-first. Per-request private streaming must verify current rights/visibility and not issue reusable signed URLs.
4. **No PUBLIC promotion until risk closed:** keep known old public object/CDN links and externally archived copies classified. Do not bulk alter PUBLIC bucket ACL or rotate credentials without counting affected applications, dependent services, 4,720 historical objects/166 candidate estimates (2026-10-29 survey, **not current live counts**), rollback and restoration plan, independent rights/security review, and **separate exact user approval**.
5. **Release gate:** after a real production-aware writer fence and key isolation are verified in authorized nonprod account, run adversarial cross-credential S3/REST/TUS tests on new keys, wrong buckets, opaque extensions/MIME, signing token misuse, direct S3 path without app, same-key overwrite, stale session, revoked rights/R18, DB CAS failure, PUBLIC URL attempt, and clean rollback. Fixed-HEAD genuinely independent S2/S3/S4 audit is required before merge; CI/Preview READY alone not enough.
