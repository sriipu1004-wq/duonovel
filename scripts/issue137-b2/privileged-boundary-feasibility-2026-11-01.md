## 2. Security objective and threat boundary

Goal: keep authorized Human user-JWT PRIVATE staging distinct from AI/Human finalization, sensitive DB maintenance, audio playback and public-media writers; prevent withdrawn consent/ownership/R18/publication from enabling new access, and detect/reject accidental or adversarial alteration of promoted audio bytes. Preserve Original/Bilingual/Translation Reader behavior, provenance, valid Human/Nemo/Aivis operations and existing content. Do **not** claim WORM/physical immutability or proof of Production protection without an independently enforced writer boundary.

Important distinction: the published Supabase secret/service-role key is a project-wide `service_role` credential (BYPASSRLS); Storage S3 access keys likewise bypass Storage RLS across buckets. An authenticated **user session token** is RLS-scoped. Neither a TypeScript import allowlist, unique object path, `upsert:false`, digest+CAS, a child process, nor adding a separate web project that retains the original service key can make that privileged key bucket-scoped or immutable. Multiple secret keys from the same Supabase project improve rotation isolation but do **not** grant different bucket-level privileges.

Official sources: [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys), [Storage RLS and bypass](https://supabase.com/docs/guides/storage/security/access-control), [S3 session vs access keys](https://supabase.com/docs/guides/storage/s3/authentication), [Vercel project/environment variables](https://vercel.com/docs/environment-variables). The Vercel docs describe project/team/environment-level configuration, not verified per-function independent secret custody in this deployment.

## 5. Decision and falsifiable acceptance for the NEXT separately approved nonproduction runtime phase

1. **Current decision:** Do not deploy a new credential, worker, gateway, Supabase project or WORM provider now. Existing SOURCE and local negative tests already answer whether an unrestricted same-project admin key is safely fenced by app-side restrictions: **it is not**. No value in repeating the same basic SHA/CAS or import-graph demos.
2. Before any runtime integration, define the minimum authorizable operation per actor (Human stage, trusted Human finalize, AI generator, Reader bytes, visibility/delete maintenance). Draw a complete caller → credential → Supabase API → bucket/path dependency and verify actual deployment-level credential custody. Mark all claims that require real provider/secret isolation **UNVERIFIED**, not PASS.
3. In a future isolated test only (not this decision phase), run the exact negative: an unrelated credential-bearing path attempts a same-key `upsert:true` between provider byte-read and CAS, and after seal. The acceptance condition must include an **enforced denial** by the provider/real credential boundary, OR an explicit documented weaker 'detect-and-HOLD' security objective with no claim of immutability. Also test anonymous/other-user/R18 OFF/consent withdrawal, old signed part token lifetime, restart/ACK-loss, original/AI provenance and 1GiB bounded-memory paths.
4. If independent custody cannot be achieved cheaply, do not launch under an implied WORM claim. Reassess whether lower-cost detection/quarantine is sufficient to meet a *separately agreed* product security objective, and retain HOLD for any unclosed R18/rights/public leakage. No safety requirement is silently weakened.
5. Separate release gates: F1/F3/F4, historical PUBLIC/CDN media, authenticated Reader/owner/R18 E2E, #150 latency/AbortError and recoverable DB + Storage byte backups. Actual independent fixed-HEAD security audit is required at a stable high-risk release candidate, **not** for every isolated source/test commit. Subsequent user-specific approval is required for merge, hosted RLS/Storage/credential changes and media migration.
