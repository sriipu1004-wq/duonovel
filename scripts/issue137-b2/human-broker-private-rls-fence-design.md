# Issue #137 / PR #153 — LOCAL broker-only PRIVATE Storage RLS fence

Date: 2026-10-31. Approved phase is **disposable local PRIVATE bucket Storage policy + source/real E2E** for denying unbrokered direct JWT writes, expiry, revocation and concurrent first-write. No existing app author/Reader endpoints, Production provider/Storage/RLS/ACL/keys, migration, bucket, rights/DB data, merge or release changes.

## Boundary and architecture

- Existing \`f2p-rls-user-stage\` fixture deliberately grants any valid owner JWT INSERT under an owner path and therefore bypasses the optional one-time broker. **It remains unchanged** as a negative historical control.
- New \`f2p-broker-private-stage\` is created only by \`scripts/issue137-b2/human-broker-private-rls-fence-local.sql\` inside disposable Docker. It is PRIVATE and has an additional local bucket-publicity trigger. It grants no public URL and no ordinary user-JWT INSERT. A normal actor JWT can read the actor's own private bytes, but cannot INSERT/UPDATE/DELETE. No RLS/ACL is modified for a deployed bucket.
- A **separate authenticated synthetic GoTrue broker principal** carries a server-issued, signed \`app_metadata.libread_local_broker=true\` claim and its user ID is recorded in a protected local internal table. The browser owner never receives this broker JWT. User-controlled \`user_metadata\` is not trusted. This differs from an unrestricted Supabase service-role token: RLS still applies to the broker principal.
- Local Storage INSERT RLS includes an additional **RESTRICTIVE policy** so a different permissive policy cannot authorize direct ordinary JWT writes. It calls \`libread_internal.issue137_human_broker_can_insert(bucket_id,name)\`, a test-only **SECURITY DEFINER** helper in an unexposed internal schema (EXECUTE removed from PUBLIC, granted only to authenticated). It verifies the broker signed app metadata and ID, exact \`owner/<actor UUID>/<object UUID>.wav\` path matching a **claimed** one-use permit, nonexpired deadline, active matching \`auth.sessions\`, and fresh synthetic owner/consent/rights flags. A broker JWT alone, an expired permit, or revoked consent/session remains insufficient. Restrictive UPDATE and DELETE policies deny mutation by authenticated users in this bucket.
- This is a **test-only security-definer/Storage-schema policy experiment**. Before any production adaptation it needs a separate least-privilege/side-effect analysis for schema USAGE and default EXECUTE grants, performance of repeated RLS lookups, RLS operation semantics, lock ordering, and API/request identity, as well as a genuinely independent reviewer. Supabase recommends treating Storage schema as provider-owned and not assuming metadata policy controls physical object bytes under arbitrary privileged S3 writes.

## Evidence tests and explicit risk boundaries

\`scripts/issue137-b2/human-broker-private-rls-fence-e2e.mjs\` connects to real ephemeral local GoTrue, Postgres and Storage with synthetic users (ordinary owner, outsider, broker). Synthetic account setup/test cleanup may use local service-role credentials **inside the test harness only**. The successful write POST uses **broker's authenticated JWT, not a service-role JWT**, and PRIVATE readback uses the owner's JWT. This test imports the prior no-signed-URL one-shot broker candidate. Its local DB adapter issues and atomically consumes permits, then passes bytes to an injected synthetic PRIVATE Storage stage using a restricted broker principal.

Test obligations:
- Missing/unclaimed permit: owner JWT, other user JWT, anonymous key, and broker JWT direct POST all rejected.
- Claimed permit: owner JWT still denied even for the permitted path; broker JWT may INSERT exact new path once; original WAV SHA-256 verifies under owner-authorized PRIVATE download; anonymous public object URL denies.
- Same key replay and x-upsert prohibited; exact bytes remain unchanged. Competing concurrent network POST to the same claimed path yields exactly one successful first write.
- Expire a claimed permit in **disposable DB** and verify RLS denies Storage POST. Revoke consent, owner rights, or rights flag *after* claim and verify RLS denies. Global GoTrue logout removes the owner's real \`auth.sessions\` record; already claimed permit becomes unusable to broker.
- Attempt PRIVILEGED synthetic bucket \`public=true\` and verify it stays PRIVATE. Do not confuse bucket permission checks with control of all project S3 keys. No real Human app route or browser E2E, real consent/series/episode R18 checks, user data, old signed multipart token or multipart-scale streamed bytes are tested.

**Remaining limitations:** This is *not* cross-system atomicity. Permit consumption occurs before Storage PUT; a failed PUT leaves consumed permit, and if consent is revoked after Storage's RLS check but before bytes finish writing, DB and byte-store updates are not a single transaction. The broker-only JWT is a server credential: its compromise or unintended exposure would invalidate this model. A fully privileged \`service_role\` or Dashboard-generated S3 key can still bypass RLS, and existing Human client-signed URLs are unchanged. Server-only identity isolation must be enforced at actual deployed boundaries, with correct key management, rights/R18/consent integration, byte immutability, rate/size limits, orphan reclamation, and independent restore verification before considering release.
