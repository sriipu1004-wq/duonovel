# Issue #137 / PR #153 — Human signed multipart disposable-token proof

Date: 2026-10-31. Approved scope: **test-only** real disposable local GoTrue/Storage proof of signed upload issuance, unauthorized path use, upsert replay, session logout and temporary cleanup. Absolutely **no** Production DB/Storage/keys/ACL, migration, runtime author/Reader endpoints or merge. No signed bearer tokens, user passwords, access keys or signed URLs may be printed to CI/GitHub comments.

## Source facts and trust model

1. `human-upload-session/route.ts` authenticates the request with a user-scoped Supabase client, reads series/episode access, and then uses **`createAdminClient().storage.from(session.bucketName).createSignedUploadUrl(part.objectPath,{upsert:true})`** to issue tokens. It does **not** query the global Human recording consent before minting signed temporary upload tokens. An existing consent check occurs in `human-upload-finalize/route.ts`, **before** the final assembly's `try/finally` cleanup boundary.
2. `humanMultipartUploadShared.ts` builds `human-temp/<series>/<episode>/<user>/<session>/part-NNNN.<ext>`. The part size is 8 MiB and the multipart threshold is 4 MiB. Session IDs and path names are not revocation mechanisms; path containment alone cannot restrict possession of an already-issued signed upload token.
3. `RecordingStudioPage.tsx` uploads each browser `Blob` using `supabase.storage.from(bucket).uploadToSignedUrl(path, token, blob)`. The browser gets a bearer capability, not service-role credentials. **An attacker with the bearer token could attempt the same upload** even without the original user's cookie.
4. Supabase [createSignedUploadUrl JS reference](https://supabase.com/docs/reference/javascript/storage-from-createsigneduploadurl) specifies signed upload URLs are usable **without further authentication** and valid for **two hours**. Token expiration/invalid signature may be checked at Storage, but standard GoTrue logout or changing an application consent value does **not by itself prove** the Storage bearer token revoked.
5. `human-upload-finalize/route.ts` performs session-scoped admin reads and checks each part's **byte length**, then analyzes the concatenated file; it does not compare pre-authorized per-part SHA256 digests. A changed equal-length part can therefore evade the *size-only* condition, while the later audio analysis/atomic consent gates may still reject the finished content. This is a design risk, **not proof of unauthorized publication**.
6. `finally` in finalization removes temp paths via service-role Storage. Failures **before** entering that `try` (including unauthorized/consent failure) do not trigger this cleanup. Deleting an object does not necessarily invalidate an outstanding signed upload capability: test and document any token-based recreation.

## Disposable real-protocol negative test

`scripts/issue137-b2/human-signed-multipart-local-e2e.mjs` imports the **actual** shared multipart path builder and uses `@supabase/supabase-js` methods for signing and uploading against a locally constrained, unlinked Docker Supabase instance. It creates a brand-new synthetic PRIVATE bucket `f2p-human-signed-temp` and an ephemeral real GoTrue user, with a two-part file of 8 MiB + 96 bytes; all credentials are throwaway. Local service-role is **restricted to the test harness** and has no path to Production.

Tests: isolated PRIVATE bucket, actor/session/part path, unprivileged signature issuance denied, forged token rejected, stolen signed token for wrong path denied, anonymous token-bearer actual upload, byte-exact PRIVATE download, anonymous PUBLIC GET denied, GoTrue global signout and then existing token usage, equal-size replay/upsert mutation, finalization-style admin cleanup and existence check, post-cleanup replay attempt and second cleanup if necessary. The script distinguishes **observed** rejection from **observed** bearer-capability success and logs only classifications and assertion counts. It does not treat bearer acceptance as a PASS for authorization; accepted post-logout/replay/recreation should be recorded as **RISK / MERGE HOLD**.

This harness does **not** call deployed Next.js `/api/recordings/human-upload-session` or `.../finalize`, synthetic series/consent/R18 rows are not used, it does not assert the app's authorization predicates executed in a browser, and it does not demonstrate actual publication. Local GoTrue logout is not identical to an app-level recording-consent revocation. No signed-token hard expiry window is elapsed or simulated.

## Containment implications / release gate

Possible remedies for separate future approval: require renewed per-part scope/session/consent at a provider-enforced upload gateway; avoid `upsert:true` for tokens when immutability is required; use unique PRIVATE staged objects plus bound digests, time-limited capability revocation or private orphan cleanup, and revalidate actual request/session/owner/rights/R18 before final commit/streaming. **Do not silently rotate credentials, disable S3, change RLS, revoke existing user uploads or merge this Draft.** Final independent S2/S3/S4 fixed-HEAD audit and exact Production release authorization remain mandatory. Existing service-role bypass, B2/H1/H2/F2-P and historical PUBLIC media gates remain **FIX / NO-GO**.
