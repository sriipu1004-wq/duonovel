## Approval and isolation

The owner authorized **only design comparison and nonproduction-only implementation/negative tests** for owner/consent/session-linked short-lived one-time writing. No actual Human author API, Reading endpoints, Production Vercel/Supabase settings, credentials, migrations, RLS/ACL, preexisting files, signed token issuance or merge were changed. This is **not a release candidate** and is not an assertion that one-shot capability, Storage, and database are atomically coupled. Prior signed-URL replay and service-role bypass remain security FIX / Production NO-GO.

## Alternative architecture comparison

| Candidate | Advantage | Critical failure/limit | Current recommendation |
|---|---|---|---|
| A. Existing privileged \`createSignedUploadUrl(...,{upsert:true})\` and browser \`uploadToSignedUrl\` | Small upload can bypass app-server byte proxy; existing implementation works | Supabase signed bearer token works without subsequent user login, nominally valid 2 hours; actual local tests showed POST after GoTrue logout, same-key overwrite, re-creation after admin cleanup | **Do not reuse for sensitive Human multipart until revoked/immutable behavior is provider-enforced** |
| B. End-user JWT direct Storage upload under path-owner RLS | Avoids service-role / S3 key in browser, bucket is PRIVATE | Ordinary JWT remains usable until its access-token expiry; path owner policy alone cannot re-check current consent or \`auth.sessions\` or ensure a one-shot per-part write; a client can bypass an optional application broker | Good private-only staging baseline, NOT a full control |
| C. Private application gateway with short-lived nonce + fresh owner/session/consent check, SHA binding, one-time atomic DB claim, PRIVATE first-write-only Storage | Can reject stale consent, wrong user/session, expiry and replay **before** a Storage PUT; no signed Storage URL is returned to browser | Must be the *only* upload path at provider/network/RLS boundary. DB claim then Storage PUT is not one atomic transaction; failures leave consumed permit/orphans; post-claim revocation race remains unless Storage policy enforces it too. App-server network/CPU/streaming cost, 8 MiB/1 GiB uploads and concurrency/cleanup must be designed. | **Selected for isolated proof only, not production deployment** |
| D. Proxy with server-owned privileged secret | Easier to block direct browser Storage writes if privileges are never exposed | Concentrates service-role bypass in the proxy; dangerous if gateway compromised or alternate holders remain; requires credential inventory, least privilege, audit and rollout | Potential later architecture subject to separate approval and independent audit |

Supabase references: [signed upload URL](https://supabase.com/docs/reference/javascript/storage-from-createsigneduploadurl) states a bearer token needs no further authentication and lasts two hours; [user sessions](https://supabase.com/docs/guides/auth/sessions) explains \`session_id\` can be checked against \`auth.sessions\` after logout. These are product semantics, **not automatically enforced on an existing signed URL**.

## Current NON-WIRED proof

- \`scripts/issue137-b2/human-one-shot-broker-local.mjs\` is a localhost-only module (requires \`DO_NOT_CONTACT_PRODUCTION=true\`, \`B2_EPHEMERAL_CONFIRM=local-only\` and exact loopback URL). It accepts a **legacy anon API key** and a *fresh per-request user JWT*, verifies \`authenticated\` claims and GoTrue \`/auth/v1/user\`, and requires an injected DB adapter with \`issueAtomic\` / \`claimAtomic\` and a PRIVATE-only stage writer. **No S3 access key, signed Supabase URL or service-role key is accepted by this module.** The API returns an opaque \`permit UUID + 256-bit secret\`, with only SHA-256 of the random secret stored in DB.
- \`scripts/issue137-b2/human-one-shot-broker-local.sql\` creates two test-only tables inside \`libread_internal\` with no anon/authenticated/service_role table grants or exposed RPC. Each permit binds actor, GoTrue \`session_id\`, unique object ID and **expected exact bytes SHA-256**, expires no later than 30 seconds, and records \`claimed_at\`.
- \`scripts/issue137-b2/human-one-shot-broker-e2e.mjs\` uses actual localhost GoTrue + PostgreSQL \`auth.sessions\` (via **test-harness-only** Docker psql) and the already-tested user-JWT PRIVATE Storage writer. Issuance and one-time consumption check *fresh* \`recording_consent\`, \`owner_allowed\`, \`rights_allowed\` and matching \`auth.sessions\` in actual PostgreSQL. An atomic \`UPDATE ... WHERE claimed_at IS NULL AND expires_at > clock_timestamp() ... RETURNING object_id\` consumes the permit BEFORE any Storage upload. If writing fails thereafter, the permit stays consumed. A unique owner-scoped path permits PRIVATE first-write storage; x-upsert/replay are denied by the existing local RLS fixture.
- Actual negative tests: wrong principal, corrupted bearer, same-length altered bytes, exact-token replay, racing two claimants (exactly one may reserve), consent/ownership/rights revoked *after issue*, issue denied after consent revoked, expired TTL via test-clock DB update, logout and stale JWT checked against deleted \`auth.sessions\`, no public read, same-key x-upsert denied and stored bytes preserved, admin cleanup then no token-based resurrection, test-module rejection of service JWT as identity and non-loopback URL. **No real consent revocation or stream of 1 GiB Human multipart through the app API is tested.**
- **Required negative control:** existing \`f2p-rls-user-stage\` owner-path Storage RLS still lets an authenticated owner use direct REST POST without going through the broker. The E2E intentionally observes and removes this test-only object; this **proves provider-side issuer/bucket isolation is still needed** before actual deployment. The broker must not be described as eliminating this parallel path.
- Existing service-role S3/Storage direct PUBLIC bypass and historical PUBLIC/CDN bytes are completely unaffected. No eligible production publication path or Human session issuance route is wired to this candidate.

## Release blockers and follow-up design questions

1. Enforce sole upload entry at a future **separately authorized nonproduction provider gateway/RLS layer**, disallow user-supplied bearer/storage bypass, and keep original PUBLIC bucket inaccessible to direct writers. Authenticated owner-path RLS alone is **not sufficient**.
2. Implement real per-part first-write immutability and byte digest checks at the trusted provider path. The current SHA is bound by the broker immediately **before** staging; service-role/S3 alternate writers still bypass the broker. No cross-store atomicity: a claim may be consumed while upload fails. Need idempotent deterministic recovery, orphan TTL cleanup, and backup/restore proof.
3. Consent and rights are **synthetic local fixture flags**, not the real User Recording Consents / episode ownership/publication/R18 policies. Must connect to genuine live-domain checks only with a new authorized implementation phase and independent reviewer. \`auth.sessions\` existence is checked for this local test, but terminal-session cleanup and stale access-token handling in real runtime remain unverified.
4. Human 8 MiB signed multipart parts / up to 1 GiB total cannot be served by this current small (<=1 MiB) test-only WAV writer. Define upload bandwidth/abort handling, timeouts, chunk concurrency, quota, claims/bytes binding and cancellation cost before any rollout.
5. Existing client-signed two-hour token issuance and finalize cleanup path remain **UNMODIFIED**. Do not claim source/mock/LOCAL test is browser/Preview/Production integration or an independent S2/S3/S4 GO.

**Disposition: FIX / MERGE HOLD / Production B2/H1/H2/F2-P NO-GO.** No deployment, real user media, Production schema, ACL, credential or key rotation is approved.
