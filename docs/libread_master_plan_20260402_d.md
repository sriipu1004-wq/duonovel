## 2. 「見せる前提」優先順位ラベル

### 2-1. ラベル定義
- **SHOW-CORE**
  - 人に見せた瞬間の印象を決める中核
  - 試作の見える化に直結
- **SHOW-DEMO**
  - 朗読と演出の強みをデモで伝えるための改善
- **SHOW-PRELAUNCH**
  - 事前集客やクラファン前に必要な導線・説明・登録ページ
- **SHOW-BETA**
  - 小さく公開して触ってもらうための最低限の安定化
- **MONETIZE-PRELAUNCH**
  - 公開前に広告導線や広告実装条件を整えるための準備
- **MONETIZE-BETA**
  - 小さく公開した後に広告掲載・計測・配置を整えるための準備
- **FOUNDATION**
  - 外から見えにくい内部整理や将来のための整備

### 2-2. 試作段階の朗読方針
- 試作段階では **Google の読み上げ TTS による自動朗読生成** を優先候補として扱う
- 対象は少なくとも **朗読許可作品** を前提にした自動朗読生成
- クラファン資金が確保できた段階で **VoicePark 等の有償音声導入** を次段階候補として扱う
- 実装直前には利用規約・ライセンス・運用条件を再確認する

### 2-3. 初期収録作品の方針
- 最初に入れておく作品は **著作権が切れている作品（パブリックドメイン作品）** を優先する
- 初期展示用コンテンツとサンプル作品の核として使う

### 2-4. 広告方針
- サイトに載せる広告の第一候補は **Google AdSense** を基本線とする
- 試作・工事中の状態では審査申請しない
- 事前集客のためにこちらから出稿する広告は **Google Ads** を候補に含めるが、掲載広告とは別物として扱う

## 4. コード差し込みの厳格ルール
- 必ず repo 実体を確認して、前後の形に厳密に合わせる
- 差し込み位置が曖昧なら、部分差し込みではなく丸ごと置換用の完成コードを優先する
- **貼り付けた時に sibling 要素の列・インデントが1つでも崩れるコードは不合格扱いにする**
- **JSX の兄弟要素は同じ深さなら同じ字下げで揃える**
- **部分差し込みで列ズレの危険がある時は、必ず親の開始タグから閉じタグまで含めた完成ブロックを出す**
- 見た目上「たまたま動くかも」で済ませず、貼る前から整形済みの完成コードを出す

## 5. 次の判断ポイント

### 5-1. 今の評価
- SHOW-CORE のうち
  - トップ
  - 作品ページ
  - 公開検索導線
  まではかなり整った
- ただし、まだ
  - 読書ページそのものの外向き印象強化
  - サービス説明 / 先行登録などの事前集客ページ
  - Google TTS 自動朗読生成の試作導線
  が残っている

### 5-2. 次に切る候補
#### 候補A
**SHOW-CORE: 読書ページ外向き印象強化MVP**
- 読書ページの密度、余白、タイポ、視線導線をさらに整える
- 「このサイトの強みは朗読と演出」と見て分かる完成度に寄せる
- 今ある機能を一番よく見せる方向

#### 候補B
**SHOW-PRELAUNCH: 事前集客ページ整備MVP**
- サービス説明
- 特徴紹介
- 先行登録 / 通知登録の導線
- お知らせ / 開発進捗の入口
- 見せた後に「追いたい」と思わせる導線を作る

#### 候補C
**SHOW-DEMO: Google TTS 自動朗読試作導線MVP**
- 朗読許可作品に対して試作段階の自動朗読を成立させる
- パブリックドメイン作品の初期サンプル投入と相性が良い
- デモとして強いが、UI印象整備よりは一段あとでもよい

### 5-3. 親チャットの推奨順
- まずは **候補A**
- 次に **候補B**
- その後 **候補C**

理由:
- いま最優先は「人に見せた瞬間の完成度」
- 検索導線まで整ったので、次は読書ページをさらに磨くと試作の見える化が一段完成する
- その後、事前集客ページを置けば見せた相手を逃しにくい
- Google TTS は強い見せ場だが、見た目と説明導線が整ってから載せる方が刺さりやすい

## 6. 同期と docs 運用
- GitHub にあるだけで local に無い状態は、正史確認には使えても実作業継続前提にはしない
- 次の作業前に必ず local を同期する
- 用語を分ける
  - repo正史反映済み
  - local反映済み
  - 両方反映済み
- 「反映済み」は原則、GitHub と local の両方が揃った時だけ使う
- docs cleanup は毎回必須ではない
- 重複 docs が新たに増えた時だけ cleanup 対象にする
