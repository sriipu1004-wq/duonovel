---

## 1. 子チャット作業の前提

- 子チャットの役割は **VS Code の local ファイル変更指示を出すこと**
- 実際に動かすのはユーザー側とする
- 子チャットは「こちらが動かす前提」で話を進めない
- 以後の実装指示は、原則として **local に存在するファイルをどう直すか** を中心に出す

補足:
- repo 上に変更があっても、それだけで実装前提を確定しない
- local に対象ファイルが存在し、ユーザーがそこで変更できることを重視する

---

## 2. repo 確認と VS Code local のズレ

- 親チャットが repo 確認を行った時、**repo と VS Code local のズレが見つかったら再判定** を出す
- repo 側で進んでいても、local が追いついていなければ、そのまま次作業へは進めない
- 逆に local だけ進んでいて repo に無い場合も、正式受理や次段階移行は保留する

再判定が必要な例:
- repo の commit は存在するが、local HEAD が一致していない
- local には未反映で、対象ファイルが VS Code 上に無い
- GitHub だけ更新済み、または local だけ更新済み
- 子チャット報告と repo 実体確認が噛み合わない

---

## 3. 正式受理と次作業移行の条件

- 親チャットが正式受理する時は、原則として以下を分けて確認する
  - repo 正史
  - VS Code local
  - 同期済みかどうか
- どれかが不足している場合は、必要に応じて **保留 / 差し戻し / 再判定** を出す
- 「push 済み」だけでは不十分で、local 作業前提として成立しているかも確認対象にする

---

## 4. 子チャットへの今後の指示の出し方

- 既存子チャットで十分なら、その子チャット継続を優先する
- 新規子チャットが必要な場合は、単発名ではなく **ある程度汎用性のある担当名** を付ける
- 他チャットへ貼る必要がある長文は、以後 **TypeScript コードブロック形式** で出す

---

## 5. 親チャットで忘れないための固定ルール

以後、親チャットは次を固定ルールとして扱う。

1.
子チャットは VS Code local ファイル変更指示を出す場

2.
実際に動かすのはユーザー

3.
repo 確認時に VS Code local とのズレがあれば再判定を出す

4.
repo / local / 同期済み を分けて扱う

5.
これらが揃わないまま、次段階へ機械的に進めない
