## 2. 公開モデルの固定仕様
- 作品規模では **公開 / 非公開** を扱う
- エピソード規模では **投稿 / 予約投稿 / 下書き保存** を扱う
- **エピソード規模での公開 / 非公開という考え方は廃止** する
- series 側 canonical は `publication_status`
- episodes 側 canonical は `posting_status`, `scheduled_for`, `posted_at`, `last_edited_at`
- 既存の `is_published / published` は移行期互換として扱う
- 前話が下書きの時は次話を 投稿 / 予約投稿 にできない制約を持たせる
- 前話が予約投稿の時は次話の予約時刻を前話より前にできない制約を持たせる
- 投稿済みエピソードの編集は許可する
- 作品ページでは各話に投稿日を出し、編集済みなら投稿日の隣に編集日と編集済み表示を出す

## 3. 再生体験と閲覧演出についての固定要望
- 線が文字を追従する機能を維持・修正する
- 閲覧位置が自動でスクロールする機能を維持・修正する
- 次話自動再生ボタンを配置し、ON/OFF を切り替えられるようにする
- 演出設定は少なくともプレビューどおりに作品閲覧ページへ反映されることを目標にする
- 作品閲覧ページの朗読フッターは中央揃えで、再生ボタンが真ん中に来る構成へ統一する
- 左から `栞 / 現在位置に戻る / 前話 / 再生 / 次話 / 自動追尾 / 設定` の順で置く
- フッター内のそれ以外の要素は削除する
- **自動追尾中は反応無し** とする

## 4. 作者向け / 演出の固定方針
- 作者向け主導線は **作品ワークスペース中心**
- `/write` = 作品ワークスペース一覧
- `/write/series/[seriesId]` = 作品ワークスペース本体
- `/manage` と `/manage/series/[seriesId]` は backward 互換 redirect
- `WriteEpisodeForm.tsx` は **本文編集中心**
- 演出は **既定演出設定** と **演出編集** に責務分離して扱う
- **既定演出設定** は作品共通の既定値を置く場所
  - 共通BGM
  - 既定フォント
  - 既定文字色
  - 既定背景
  - 作品共通のプレビュー確認
- **各話演出編集** はその話限定の設定を置く場所
  - 各話BGM
  - その話限定の背景
  - 文字演出
  - 挿絵
  - 場面転換
  - その他その話固有の演出
- 今後の機能追加でも、この割当を崩さない

## 5. 子チャット運用の正式テンプレ

### 5-1. 新規子チャット前提文の正式ルール
- 子チャットの役割は **VS Code local ファイル変更指示を出すこと**
- 実際に反映・実行するのはユーザー側
- GitHub 上に存在しても、VS Code local に無いファイルを前提に実装を進めない
- repo にあること、local にあること、push 済みであることを分けて確認する
- repo と VS Code local にズレがあったら、その場で再判定を出す
- コードはコピペしやすい完成形で出す
- どのローカルファイルを開いて、何をどう置き換えるかまで具体的に示す
- エラーが出たら原因候補を切り分ける
- まず全体像を見失わないことを優先する
- 仕様が広がりそうなら、勝手に広げず親チャット再判定前提で止める
- 正式な報告先は親チャットのみ
- 子チャットから別の子チャットへの正式引き継ぎ文は作らない
- チャットが重くなった場合も、子チャットは親チャット向け報告のみを出す
- 次の子チャットへ渡す正式な引き継ぎ文は親チャットが作る

### 5-2. コード差し込みルール
- 必ず repo 実体を確認して、前後の形に厳密に合わせる
- インデント、改行位置、JSX の入れ子、閉じタグ、閉じ括弧、条件分岐の開始位置と終了位置まで合わせる
- 差し込み位置が曖昧なら、部分差し込みではなく丸ごと置換用の完成コードを優先する
- repo と local に差がある時は、その差を踏まえて安全な置換単位で出す
- 見た目上ずれているだけに見えても危険なので、形が崩れたコードは出さない

### 5-3. 作業ルール
- まず最初に、今回の目的、触る範囲、やらない範囲を短く整理する
- 変更前に、対象ファイルが local に存在するか確認する
- 変更前に、repo 実体と local 実体の差を意識する
- 1回で広く触りすぎず、今回のゴールに必要な最小変更で到達させる
- 動いた後に余計な拡張をしない
- docs を参照する場合は、正史本体を優先する
- 新しい引き継ぎ文が出た時点で、旧差分管理は自動的に終了扱いとする
- 子チャットは、ユーザーが「今回の担当範囲は完了」と判断した時だけ親チャット向け報告テンプレを完成させる

### 5-4. 親チャット再判定条件
- 想定より触るファイル数が広がる
- DB / Supabase スキーマ変更が必要になる
- ルーティングや画面責務の再設計が必要になる
- 既存の固定仕様同士が衝突する
- repo と local のズレが大きく、安全な置換単位で出せない
- 直すつもりのない別系統の不具合まで巻き込みそう
- 当初の差分管理名で収まらない新仕様が発生する

### 5-5. 子チャットの毎回の出力形式
- 現在地
- 今回の目的
- 触る範囲
- 影響範囲
- 今回のゴール
- 実装 or 調査結果
- 動作確認項目
- 必要なら同期手順
- 必要なら親チャット向け報告テンプレ

### 5-6. 同期ルール
- 動作確認が済んで次が同期だけになったら、同期の指示を出す
- 同期が完了したら、同期内容を引き継ぎ文に加えた全文を出す
- 子チャットの同期作業指示には、必要時のみ docs cleanup を含める
- docs cleanup をやる場合は、最新の正史本体だけ残し、役割の重なる古い docs を削除対象として整理する
- ただし docs cleanup は毎回必須ではない。重複 docs が新たに増えた時だけ対象

### 5-7. 同期前確認
- 対象ファイルが VS Code local に存在するか確認
- 現在ブランチ確認
- git status 確認
- local HEAD 確認
- origin/main HEAD 確認
- repo と local にズレがあれば再判定

### 5-8. 同期判定ルール
- 同期判定は途中表示ではなく最終実測値を優先する
- 次を実行後、
  - `git push origin main`
  - `git rev-parse HEAD`
  - `git rev-parse origin/main`
  - `git status`
  の結果で
  - push 成功または Everything up-to-date
  - local HEAD と origin/main HEAD が一致
  - working tree clean
  なら同期完了扱いにする
- 途中で `Your branch and 'origin/main' have diverged` が出ていても、最終的に HEAD 一致・working tree clean なら追加の rebase / pull / push は不要
- 同期判断は必ず最後の実測値で確定する

### 5-9. 子チャット引き継ぎ文テンプレの正式項目
- 使用チャット名
- 新規子チャット前提文
- 差分管理名
- 現在地
- 今回の目的
- 固定前提
- 今回まずやること
- 優先して確認するファイル候補
- 今回のゴール
- 今回やらないこと
- 次段階候補
- 完了条件
- 同期前確認
- 現在の基準同期情報
- 親チャット向け報告時に必ず入れること

- 確認対象には少なくとも次を含める
  - route
  - 型
  - helper
  - 保存先カラム / settings 構造
  - 既存コンポーネント名
- 仕様だけで判断せず、**repo 上の既存の名前と責務に結びつけて** 実装判断する
- 名前が近いから同じ責務だと決めつけず、実ファイル上の入出力と保存先を確認する

## 9. 同期と docs 運用
- GitHub にあるだけで local に無い状態は、正史確認には使えても実作業継続前提にはしない
- 次の作業前に必ず local を同期する
- 用語を分ける
  - repo正史反映済み
  - local反映済み
  - 両方反映済み
- 「反映済み」は原則、GitHub と local の両方が揃った時だけ使う
- docs cleanup は毎回必須ではない
- 重複 docs が新たに増えた時だけ cleanup 対象にする
