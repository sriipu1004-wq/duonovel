## 2. 「見せる前提」優先順位ラベル

### 2-1. ラベル定義
- **SHOW-CORE**
  - 人に見せた瞬間の印象を決める中核
  - 試作の見える化に直結
- **SHOW-DEMO**
  - 朗読と演出の強みをデモで伝えるための改善
  - 動くと強いが、見せ方の文脈が必要
- **SHOW-PRELAUNCH**
  - 事前集客やクラファン前に必要な導線・説明・登録ページ
- **SHOW-BETA**
  - 小さく公開して触ってもらうための最低限の安定化
- **MONETIZE-PRELAUNCH**
  - 公開前に広告導線や広告実装条件を整えるための準備
- **MONETIZE-BETA**
  - 小さく公開した後に広告掲載・計測・配置を実運用前提で整えるための準備
- **FOUNDATION**
  - 重要だが、外から見えにくい内部整理や将来のための整備

### 2-2. 試作段階の朗読方針
- **SHOW-DEMO / SHOW-BETA** として、試作段階では **Google の読み上げ TTS による自動朗読生成** を優先候補として扱う
- 対象は、少なくとも **朗読許可作品** を前提にした自動朗読生成
- 試作段階では、まず「自動朗読が実際に回ること」と「見せられる体験になること」を優先する
- その後、クラファン資金が確保できた段階で、**VoicePark 等の有償音声導入** を次段階候補として扱う
- ただし、実装直前には利用規約・ライセンス・運用条件を再確認する

### 2-3. 初期収録作品の方針
- **SHOW-DEMO / SHOW-BETA** として、最初に入れておく作品は **著作権が切れている作品（パブリックドメイン作品）** を優先する
- 目的は、
  - 初期展示用コンテンツを確保すること
  - 権利調整の負担を減らすこと
  - 朗読と演出の見せ場を早く用意すること
- 事前集客や試作見せでは、この初期作品群を **サンプル作品** として使う前提でよい

### 2-4. 広告方針
- サイトに載せる広告の第一候補は、**Google AdSense** を基本線とする
- ただし、**試作・工事中の状態では承認を取りに行かない**
- 広告の実装準備は公開前に検討してよいが、**実際の審査申請は、ある程度ページとコンテンツが揃ってから** 行う
- 事前集客のためにこちらから出稿する広告は **Google Ads** を候補に含めるが、これは掲載広告とは別物として扱う
- つまり
  - **Google AdSense = サイトに載せる広告**
  - **Google Ads = こちらが出す集客広告**
  で区別する

## 3. 子チャット運用の正式テンプレ
- 子チャットの役割は **VS Code local ファイル変更指示を出すこと**
- 実際に反映・実行するのはユーザー側
- GitHub 上に存在しても、VS Code local に無いファイルを前提に実装を進めない
- repo にあること、local にあること、push 済みであることを分けて確認する
- repo と VS Code local にズレがあったら、その場で再判定を出す
- 正式な報告先は親チャットのみ
- 子チャットから別の子チャットへの正式引き継ぎ文は作らない
- チャットが重くなった場合も、子チャットは親チャット向け報告のみを出す
- 次の子チャットへ渡す正式な引き継ぎ文は親チャットが作る
- 必ず repo 実体を確認して、前後の形に厳密に合わせる
- 差し込み位置が曖昧なら、部分差し込みではなく丸ごと置換用の完成コードを優先する
- **貼り付けた時に sibling 要素の列・インデントが1つでも崩れるコードは不合格扱いにする**
- **JSX の兄弟要素は同じ深さなら同じ字下げで揃える。1行だけ深く入る状態を許容しない**
- **部分差し込みで列ズレの危険がある時は、必ず親の開始タグから閉じタグまで含めた完成ブロックを出す**
- **例として `<div className="mt-3 flex flex-wrap gap-2">` の子に並ぶ `<ExploreChip />` 群のような sibling 群は、全行を同じ列で揃えた状態でしか出さない**
- **見た目上「たまたま動くかも」で済ませず、貼る前から整形済みの完成コードを出す**
- 同期判定は途中表示ではなく **最終実測値** を優先する

## 5. 同期と docs 運用
- GitHub にあるだけで local に無い状態は、正史確認には使えても実作業継続前提にはしない
- 次の作業前に必ず local を同期する
- 用語を分ける
  - repo正史反映済み
  - local反映済み
  - 両方反映済み
- 「反映済み」は原則、GitHub と local の両方が揃った時だけ使う
- docs cleanup は毎回必須ではない
- 重複 docs が新たに増えた時だけ cleanup 対象にする
