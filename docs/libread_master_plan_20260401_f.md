## 2. 今回固定する新しい公開モデル

### 2-1. 基本方針
- **作品規模** と **エピソード規模** で責務を分ける
- 作品規模では **公開 / 非公開** を扱う
- エピソード規模では **投稿 / 予約投稿 / 下書き保存** を扱う
- **エピソード規模での公開 / 非公開という考え方は廃止** する

### 2-2. 作品規模の公開状態
- 作品には **公開 / 非公開** の状態を持たせる
- この状態は **作品ワークスペースで管理** する
- 作品公開状態は、作品全体の公開面に対する責務として扱う

### 2-3. エピソード規模の投稿状態
- エピソードは次の3状態で扱う
  - **投稿**
  - **予約投稿**
  - **下書き保存**
- エピソードでは公開 / 非公開は持たせず、投稿状態だけを持たせる
- 予約投稿には投稿予定日時を持たせる前提で扱う

### 2-4. 新規作品作成時の扱い
- 新規作品作成時は、少なくとも次の2軸を選べるようにする
  - 作品公開状態: **公開 / 非公開**
  - 初回エピソード投稿状態: **投稿 / 予約投稿 / 下書き保存**
- UI 上は「公開非公開の選択」と「投稿 / 予約投稿 / 下書き保存の選択」を同時に扱えるようにする
- ここでの文面上の「4つ」は、作品公開状態とエピソード投稿状態を合わせて操作できる初回作成フローとして解釈する

### 2-5. 予約投稿 / 下書き保存時のワークスペース導線
- 新規作品を **予約投稿** または **下書き保存** で作成した場合も、**作成した瞬間から作品ワークスペースに表示** する
- その状態でも、作者はそのまま作品ワークスペースへ入り、次のエピソードを記入できるようにする
- 予約投稿 / 下書き保存は、公開面に出さないことと、ワークスペース上で管理できることを両立させる

### 2-6. 次の話の連続作成
- エピソードを **予約投稿** または **下書き保存** した場合、保存直後にそのまま **次の話を作成できる導線** を出す
- 投稿状態に応じて、作品制作の流れが途切れないことを優先する

### 2-7. 公開タイミングの扱い
- 作品公開状態が **公開** の場合、公開済みエピソードが存在するなら、その作品も公開面に出す
- エピソードが **投稿** の場合、投稿済みエピソードと作品公開状態がそろった時点で公開面に出す
- エピソードが **予約投稿** の場合、予約時刻にそのエピソードが投稿状態へ移るのと同時に、必要なら作品も公開面に出す
- 作品が **非公開** の場合は、エピソードが投稿状態でも公開面に出さない前提で扱う

### 2-8. 追加で固定しておく前提
- この変更により、episodes の公開 canonical は `is_published` だけでは足りなくなる可能性が高い
- 今後は少なくとも
  - 作品公開状態
  - エピソード投稿状態
  - 予約投稿日時
  の責務分離を前提に再設計する
- 既存の `is_published / published` 互換吸収は、移行期間の互換として扱う

## 3. 再生体験と閲覧演出についての固定要望

### 3-1. 朗読再生中の追従表示
- 朗読再生時に、**線が文字を追従する演出** を維持・修正する
- その位置に合わせて、**閲覧位置が自動でスクロールする機能** も維持・修正する
- 再生体験として重要なため、単なる装飾ではなく主要機能として扱う
- 既存 repo では仮の本文追尾処理があるため、完全新規ではなく **既存追従処理の回帰修正 / 精度改善** として扱う
- 将来的には、音声全体進行率の推定ではなく、文単位 timestamp に寄せる方向を前提にする

### 3-2. 次話自動再生ボタン
- 作品閲覧ページに **次話自動再生ボタン** を配置する
- ON の時は、朗読が終わった際に自動で次話へ移動する
- OFF の時は、再生終了後もその話に留まる
- 現状 repo では自動次話移動が固定 ON 寄りになっているため、**ボタンによる明示的な切替UI** を追加する

### 3-3. 演出プレビューと実閲覧の一致
- **演出設定は、少なくともプレビューどおりに作品閲覧ページへ反映されることを目標** とする
- preview 用描画と read 用描画が分離していて差が出る状態を放置しない
- 背景、既定フォント、文字色、ルビ、強調、挿絵、scene cue など、preview で出ている要素は read 側でも責務に応じて反映する
- 既存 repo では `EffectPreviewRenderer.tsx` が preview 用描画を持ち、`EpisodePlayback.tsx` は本文を独自描画しているため、**rendering parity の修正** を優先課題として扱う
- read 側で effect settings をどう読むか、series / episode 演出をどう合成するか、preview と read で renderer をどう共有するかを整理する

### 3-4. 作品閲覧ページフッターの固定レイアウト
- 作品閲覧ページで朗読を司るフッターは、**中央揃えで、再生ボタンが真ん中** に来る構成へ統一する
- 左から次の順で配置する
  - **栞**
  - **現在位置に戻る**
  - **前話**
  - **再生**
  - **次話**
  - **自動追尾**
  - **設定**
- フッター内のそれ以外の要素は削除する
- 既存の目次リンク、固定文言バッジ、自動次話移動ON固定表示など、上記以外のフッター要素は外す
- **自動追尾** は切替ボタンとして扱う
- **自動追尾中は反応無し** とし、再クリックで状態を切り替えるUIにはしない
- 現在位置復帰が不要な状態では、見た目の並びを大きく崩さない形で無効化または非活性表示を使う
- 再生ボタンを中心に置いたまま、左右の操作群バランスを優先する

## 4. 既存の固定方針

### 4-1. 作者向け導線
- 作者向け主導線は **作品ワークスペース中心**
- 現在の整理:
  - `/write` = 作品ワークスペース一覧
  - `/write/series/[seriesId]` = 作品ワークスペース本体
  - `/manage` = backward 互換 redirect
  - `/manage/series/[seriesId]` = backward 互換 redirect
- 作品に表示される導線のうち **管理ハブ** は削除する
- 以後は、作品ごとの実作業導線を **作品ワークスペース中心** に統一する

### 4-2. 本文編集ページ
- `WriteEpisodeForm.tsx` は **本文編集中心**
- 本文編集ページに設定を詰め込みすぎない
- 作品全体の方向付けは作品ワークスペース側で持つ
- 本文だけスクロールしやすい構造を維持する

### 4-3. 朗読導線
- 朗読の主導線は **`/record`**
- 作品ページでは朗読可否表示は残すが、申請や制作開始の主動線は `/record` に集約
- 朗読許可状態:
  - `open`
  - `closed`
  - `approval_required`
- 管理ハブ的な新導線は増やさない

### 4-4. BGM / 演出方針
- 外部持ち込みBGM前提では進めない
- サイト用意BGM中心
- `bgm_library` を素材正史とする
- BGM の「お気に入り」は **BGM素材用 favorite** として扱い、作品保存機能とは混同しない
- 演出は **既定演出設定** と **演出編集** に責務分離して扱う
- **既定演出設定** は、作品共通の既定値を置く場所
  - 共通BGM
  - 既定フォント
  - 既定文字色
  - 既定背景
  - 作品共通のプレビュー確認
- **各話演出編集** は、その話限定の設定を置く場所
  - 各話BGM
  - その話限定の背景
  - 文字演出
  - 挿絵
  - 場面転換
  - その他その話固有の演出
- 今後の機能追加でも、この割当を崩さない

### 4-5. 詳細機能追加時の確認ルール
- 詳細な機能を足す時は、**repo の実ファイルを先に確認する**
- 確認対象には少なくとも次を含める
  - route
  - 型
  - helper
  - 保存先カラム / settings 構造
  - 既存コンポーネント名
- 仕様だけで判断せず、**repo 上の既存の名前と責務に結びつけて** 実装判断する
- 名前が近いから同じ責務だと決めつけず、実ファイル上の入出力と保存先を確認する

### 4-6. コード差し込みの厳格ルール
- 子チャットがコード差し込み指示を出す時は、**repo 実体を見て前後の形を厳密に合わせる**
- 単にロジックが合っているだけでは不十分で、少なくとも次を合わせる
  - インデント
  - 改行位置
  - JSX の入れ子
  - 条件分岐の開始位置と終了位置
  - 閉じタグ
  - 閉じ括弧
  - fragment / 配列 / オブジェクトの閉じ方
- 差し込み位置の前後数行を repo 実体に合わせて確認し、**その位置にそのまま貼って崩れない形** で出す
- ずれた見た目のコードは、見た目だけの問題で済まず、条件分岐の境界や JSX 構造の誤差を見落としやすいため危険とみなす
- 特に TSX / JSX では、インデントずれや閉じ位置ずれがある時は、**正しい場所に入っていない可能性がある** 前提で再確認する
- 子チャットは、部分差し込みコードだけでなく、必要なら **丸ごと置換用の完成コード** を優先して出す
- ピンポイント差し込みを出す場合も、
  - どの行の直後に入れるか
  - どのブロックを丸ごと置き換えるか
  - 置換前後で開始タグと終了タグがどう対応するか
  を明示する
- repo 実体と local 実体で差がある場合は、**repo だけ見て形を決め打ちしない**
- local での現在の形も確認し、repo / local の両方に対して安全な置換単位で指示する

### 4-7. 反応機能の正式整理
- **ブックマーク** = 作品保存
- **いいね** = 軽い反応 / 人気度の簡易指標
- **レビュー** = 作品単位の言葉の反応
- **エピソードコメント** = 各話末尾の感想・反応
- それぞれ別機能として育てる

## 7. 親チャット / 子チャット運用ルール

### 7-1. 子チャット作業の前提
- 子チャットの役割は **VS Code の local ファイル変更指示を出すこと**
- 実際に動かすのはユーザー側とする
- 子チャットは「こちらが動かす前提」で話を進めない
- 以後の実装指示は、原則として **local に存在するファイルをどう直すか** を中心に出す

### 7-2. repo 確認と VS Code local のズレ
- 親チャットが repo 確認を行った時、**repo と VS Code local のズレが見つかったら再判定** を出す
- repo 側で進んでいても、local が追いついていなければ、そのまま次作業へは進めない
- 逆に local だけ進んでいて repo に無い場合も、正式受理や次段階移行は保留する

### 7-3. 新規子チャットの扱い
- 作品ワークスペース系の子チャットが重くなった場合は、新しく切ってよい
- 新規子チャットを作る場合は、**新規子チャット前提文付き** で渡す
- 新規子チャット名は、単発名ではなく **ある程度汎用性のある担当名** にする

### 7-4. 子チャット引き継ぎ文に必ず入れる文言
- 今後、子チャット引き継ぎ文には次の趣旨を必ず入れる
  - **コード差し込み時は repo 実体を参照し、前後の形に完璧に合わせること**
  - **インデント、括弧、JSX 構造、閉じ位置まで一致する完成コードを出すこと**
  - **差し込み位置が曖昧なら、部分差し込みではなく丸ごと置換コードを優先すること**
  - **repo と local に差があるなら、その差を踏まえて安全な置換単位で出すこと**

## 8. ユーザーから来た改善点・指示の扱い

- 親チャットは、ユーザーから送られた **改善点 / 指示 / 運用変更案** を受けた時、まず **正史へ入れるべき内容かどうか** を判定する
- 正史へ入れるべきと判断した場合は、親チャット本文だけで済ませず、**このファイルへ統合する**
- docs cleanup は **毎回必須ではない**
- 役割の重なる古い master plan / delta docs / 重複する正史 docs が新たに出た時だけ cleanup 対象にする
- 直接上書きが扱いづらい場合は、**正史ファイルと更新内容を吟味して新しい正史ファイルを作り直す**

## 9. GitHub / local 同期ルール

- GitHub にあるだけで local に無い状態は、正史確認には使えても実作業継続前提にはしない
- 次の作業前に必ず local を同期する
- 用語を分ける:
  - repo正史反映済み
  - local反映済み
  - 両方反映済み
- 「反映済み」は原則、GitHub と local の両方が揃った時だけ使う
