# 共通作業状態・次の行動プロトコル v1.1 — LIB read

**採用対象:** ユーザー提示の v1.0（2026-10-24）、今回の追加要件（優先作業枯渇・独立監査の別チャット）。**このファイルを詳細仕様の正本**とする。短縮コピーは [ChatGPT Project instructions](chatgpt-project-instructions.md)、入口は [AGENTS.md](../AGENTS.md)。既存の CONTROL-R4、[roadmap](roadmap.md)、[chat operations](chat-operations.md)、[development workflow](development-workflow.md) の**実行権限・優先順位・安全ゲートを変更しない**。

## 1. 目的と権限境界

ユーザーが回答の**末尾3行だけ**で、進捗・自分の必要操作・実際に進められる工程を判断できるようにする。回答スタイルの規約であって、新しい開発・承認・監査・本番アクセス権は付与しない。

1. GitHub現行正本、当該Issue/PRの承認範囲、security/rights/independent-review gatesを最優先する。
2. 許可済みの同一Issue・同一工程は、不要な再確認なしに進める。許可された工程を終えたらそこで停止する。未承認の新Issue・勝手なロードマップ変更・並行書き込みは禁止。
3. 「続けて」は**承認済み範囲での再開だけ**。merge、Production DB/Storage、Auth/RLS、権利状態、公開範囲、課金、広告、Cron、外部送信、実機操作、別チャット監査開始を承認する言葉ではない。「承認する」「完了」も、対象と操作が特定されなければ別件には適用しない。
4. 承認待ち・外部待ちでも**同じ許可範囲内**で独立した安全な工程が残れば進める。単に古いログを再掲する、根拠なく新しいIssueに移るなどの形式的な継続は禁止。
5. 出典・ソース点検・MOCK・CI・Preview・実認証E2E・Production・別セッション監査を区別し、未実行をPASSと呼ばない。失敗した工程は原因・試行・未解決を報告する。
6. GitHub情報は日時付きスナップショットであり、回答状態を永続的に正しくする魔法ではない。毎回必要な最新HEAD/レビュー/承認を照合する。

## 3. 状態判定と優先関係

- **安全停止:** 重大な安全性・対象同定・承認整合性の不明点により、読み取りを含め安全な影響範囲を守れない場合。単なるCI待ちでは使わない。
- **引継ぎ必要・作業停止:** チャット限界や文脈不整合で正本/承認を安全に復元できない場合。固定HEAD、作業範囲、証拠、未承認、再開条件をGitHubに記録する。
- **独立監査依頼:** 重要変更の独立監査が**必要で、別のレビューセッション/レビュアーにまだ正式に渡していない**場合。レビュー指示パケットを提示する。別チャット作成/貼付けがユーザーに必要なら明示する。自動起動したと偽らない。
- **独立監査待ち:** 固定PR HEADに対する**実際の独立レビュー依頼が開始・記録済み**で、結果（GO/FIX/NO-GO）をまだ受領していない場合。単に「必要」なだけなら依頼状態であり、待ち状態ではない。
- **承認希望:** プロダクト判断でなく実行・merge・データ変更など**対象が具体的に定まった承認**が必要な場合。承認の対象/ファイル/件数/影響/操作/失効条件を書き、一般的「承認する」を別件へ流用しない。
- **指示確認:** 選択肢や優先順位など、許可では決められない**ユーザーの意思決定**が必要な場合。すでに存在するロードマップの次Issueを「何となく」開始してよいか尋ねる用途にしない。
- **ユーザー操作:** ChatGPTが実施できないProject Settingsの貼付けや外部アカウント操作が必要な場合。場所・手順・成功確認・再開文言を書く。
- **外部待機:** CI、Vercel、第三者レビュー以外の外部サービスなどが実際に進行中で結果待ちの場合。独立監査の待機には監査専用状態を優先する。
- **優先作業なし・作業停止:** [roadmap](roadmap.md)、Open Issue/PR、未解決リスク、保留依存を最新情報で照合し、**承認済み/優先度付きの実行可能・保留中作業が本当に残っていない**ときに限る。未承認・ブロック中・監査待ちの仕事が存在するなら「優先作業なし」にしない。新たな計画/目標の指示を求め、勝手に新Issueを作らない。
- **作業完了:** 指定スコープの完了条件を満たし、成果物と検証・残件を提示できる場合。案件全体の未完了を隠す用途にしない。
- **作業継続:** 実際に安全・許可済みの次工程がある場合。他のゲートに承認/指示/ユーザー操作/監査が必要でも、**影響を分離できる同一スコープの安全工程**を継続できるなら「〜・作業継続」を使う。継続できなければ「〜・作業停止」。

**衝突時:** 重大な安全停止 → 引継ぎ不能 → 当該PRの独立監査 → 対象が具体化した承認/操作/指示 → その他外部待機 → 実行可能な作業 → 本当に優先作業なし → 完了、の順で**今ユーザーがすべき最も重要な行動を一つ**選ぶ。安全上の別阻害要因は本文に併記し、状態欄は一つだけ。すでに完了した一工程を「作業完了」と報告する場合でも、別の優先Workが承認待ちならその状況を本文に残す。

## 4. 独立監査（他チャット/外部レビュアー）の特別な扱い

独立監査は通常の S1〜S4役割切替えではなく**作者と別セッションまたは別人**のREAD-ONLYレビュー。重要なAuth/RLS/R18/Private/rights/課金/Productionの変更は、固定PR HEADに対してこれが必要。レビュアーは作者のブランチを書き換えず、結果をGO/FIX/NO-GOとしてGitHubへ記録する。

**依頼パケット（レビュー前に提示）:** RepositoryとPR/Issue URL、固定HEADとbase SHA、対象差分/リスク、未検証の負例、CI・同HEAD Preview、Production SHA、厳格READ-ONLY・秘密非開示・禁止事項、GO/FIX/NO-GOの証拠記録先を含める。ChatGPTから他チャットを自動生成・送信・起動したとは宣言しない。ユーザーが別チャットを使う場合は、コピー可能な完全な依頼文と「別チャットへ貼り付け→監査結果をPRに記録→この窓口に完了を伝える」の手順を示す。

- `独立監査依頼・作業継続`: 監査をまだ依頼していないが、同じ許可スコープで安全な独立作業がある。
- `独立監査依頼・作業停止`: 依頼パケットを提示済み、別セッションへの依頼が次の唯一の工程。
- `独立監査待ち・作業継続`: 実際に依頼済み、作者は変更が監査HEADを無効にしない範囲で安全な検証・資料整理を進められる。
- `独立監査待ち・作業停止`: 実際に依頼済み、結果がないと安全に次工程へ進めない。GOまではmerge禁止。FIXなら限定修正、新HEADで再監査。

**監査依頼の時点（2026-10-29ユーザー指示・Draft提案）:** 通常の非本番テスト、隔離fixture、SOURCE/MOCK/CI作業の途中コミットでは、実運用の認証・R18・権利・公開・権限・DB・政策を変更しない限り、独立監査を毎回依頼せず、このチャットで実測と自己点検を続けてよい。重要な実装変更では、許可済みの作者側FIXとテストをまとめて進め、**安定したリリース候補の固定PR HEAD**で必要な別セッション/独立レビュアーのGO/FIX/NO-GOを求める。安全上必要なら設計途中の外部レビューも可能。検証対象のテストだけが限定GOでも、アプリ本体の未修正FIXを解除しない。すでに独立GOを得たHEADからコードが変わった場合は、新HEADに対する独立判定（適切な範囲の差分再監査を含む）が必要で、旧GOの自動継承は禁止。独立FIXはmerge停止条件であり、同じ承認済み工程の作者側修正まで禁止する意味ではない。この原則は正式なレビュー義務・merge/Productionの明示承認を緩和しない。

同一HEADが変わったら旧GOを流用せず新HEADを凍結しなおす。査読者がコメントできない/到達できない場合、実行済み監査と見なさず依頼状態または安全停止/指示確認に戻す。自動作業の背景進行を約束しない。

## 5. 回答末尾の固定形式（必須）

すべての**作業報告**は、次の**3行**を**最終行**として使用。各行は1行で完結させ、最後に追記しない。本文には通常の Git/Production, Changed, DB/Data, Preserved, Validation, Remaining, Canonical docs, Next を必要十分に記述。

```text
【現在】達成したこと・未完了・最大の制約を簡潔に記述
【次の行動】ユーザーが送る言葉、承認すべき具体的範囲、必要操作、または待機中に不要な操作を記述
【状態】上記17種類の正規状態名を完全一致で1つ記述
```

- 通常継続: 【次の行動】「続けて」で既存の許可範囲を再開。未承認のmerge/実機/Production権限は増えない。
- 優先作業枯渇: 【次の行動】新しい目標や優先順位を指示。自動で新Issueは作らない。
- 独立監査依頼: 【次の行動】固定HEAD付き監査パケットを別のChatGPTチャット/レビュアーに渡し、PRへGO/FIX/NO-GOを記録してもらう。
- 独立監査待ち: 【次の行動】レビュー結果を受領後、固定HEADとの一致を確認して再開。まだGOではない。
- Project Settings未反映: 【次の行動】Settingsで正本を貼付け・保存・再表示確認し「完了」と連絡。

**GitHubへの記録があっても、実際のChatGPT Project Settings UIは自動更新されない。** 本文のコピーはユーザーが貼付けて検証するまで「未反映」。GitHub上のDraft PRはmerge承認前にmainの正本にならない。

## 6. 検証・変更手順

このプロトコルの変更は、専用ブランチとDraft PRで行い、状態リスト、追加条件、末尾3行、ChatGPT Project Settingsの文字列、既存安全ゲートとの矛盾を静的検査する。低リスクの文書編集は自己点検と明示merge承認で足りる場合があるが、**独立監査の要否・権限の緩和を伴うルール変更には別セッションの監査を適用**。ユーザーの別途承認なくmergeしない。
