## 1. 直近の判断更新
- `予約投稿公開状態不達調査MVP` の報告を受理する
- episode 7〜9 は `posting_status = scheduled` かつ `scheduled_for <= now()` なのに、DB の物理状態としては
  - `is_published = false`
  - `posted_at = NULL`
  のままである
- 現在の公開判定 helper `isEpisodePubliclyVisible()` は、`scheduled` でも `scheduled_for <= now` なら公開扱いにできる土台がある
- `works` と `read` はこの helper ベースへ進んでいる一方、`ranking` と `readers` は旧判定を残している
- したがって、親チャット判断としては **方針B（DB 物理更新を先に入れず、全画面の公開判定を `isEpisodePubliclyVisible()` に統一する）を先に採る**

---

## 2. 方針A / 方針B の判断

### 採用方針
**方針B を先に採用する**
- DB 更新なしで全画面を `isEpisodePubliclyVisible()` に統一する
- まずは表示 / 集計 / 公開判定の不一致を解消する

### 理由
- 既存 helper に `scheduled_live` 扱いの土台がすでにある
- `works` と `read` は新判定寄りに進んでおり、修正範囲は `ranking` / `readers` など旧判定残骸の吸収に集中できる
- cron / job / scheduler 不在の状態で DB 物理更新を先に入れると、別途運用基盤の設計が必要になり広がりやすい
- まず公開判定の一貫性を取り戻す方が、最小修正で visible な不整合を減らせる

### 保留する方針
**方針A は後段で再検討する**
- 到達時に DB を
  - `posted`
  - `is_published = true`
  - `posted_at` 埋め
  へ更新する物理状態遷移は、必要なら後で入れる
- ただしそれは scheduler / cron / job / hook 相当の設計に広がるため、今回は先にやらない

## 9. コード差し込みの厳格ルール
- 必ず repo 実体を確認して、前後の形に厳密に合わせる
- 差し込み位置が曖昧なら、部分差し込みではなく丸ごと置換用の完成コードを優先する
- 貼り付けた時に sibling 要素の列・インデントが1つでも崩れるコードは不合格扱いにする
- JSX の兄弟要素は同じ深さなら同じ字下げで揃える
- 部分差し込みで列ズレの危険がある時は、必ず親の開始タグから閉じタグまで含めた完成ブロックを出す
- 見た目上「たまたま動くかも」で済ませず、貼る前から整形済みの完成コードを出す
