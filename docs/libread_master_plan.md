## 2. 現在の固定方針

### 2-1. 作者向け導線
- 作者向け主導線は **作品ワークスペース中心**
- 現在の整理:
  - `/write` = 作品ワークスペース一覧
  - `/write/series/[seriesId]` = 作品ワークスペース本体
  - `/manage` = backward 互換 redirect
  - `/manage/series/[seriesId]` = backward 互換 redirect
- 管理トップは軽い入口として扱い、作品ごとの実作業は作品ワークスペースへ寄せる
- 作品に表示される導線のうち **管理ハブ** は削除する
- 管理ハブの役割は、すでに作品ワークスペースへ統合済みとみなす
- 以後は、作品ごとの実作業導線を **作品ワークスペース中心** に統一する

### 2-2. 本文編集ページ
- `WriteEpisodeForm.tsx` は **本文編集中心**
- 本文編集ページに設定を詰め込みすぎない
- 作品全体の方向付けは作品ワークスペース側で持つ
- 本文だけスクロールしやすい構造を維持する

### 2-3. 朗読導線
- 朗読の主導線は **`/record`**
- 作品ページでは朗読可否表示は残すが、申請や制作開始の主動線は `/record` に集約
- 朗読許可状態:
  - `open`
  - `closed`
  - `approval_required`
- 管理ハブ的な新導線は増やさない

### 2-4. BGM方針
- 外部持ち込みBGM前提では進めない
- サイト用意BGM中心
- `bgm_library` を素材正史とする
- 既存 read 側互換のため、当面は `bgm_title / bgm_audio_path / bgm_settings` 併用
- BGM素材ページは **ユーザー向け公開素材ライブラリ + 自分専用の素材投入・管理基盤** として育てる
- BGM素材追加は **運営側のみ**、一般ユーザーは不可
- BGM管理ページ内にある **管理ハブ** 導線は削除する
- BGM管理ページの戻り先は **作品ワークスペース一覧** を基準にする
- 作品ワークスペース一覧から **BGM管理ページへ入る導線** を用意する
- **基本BGMの選択** は **基本演出ページ** で行う
- **エピソードごとのBGM** は **各話の演出編集ページ** で行う
- 現在の **BGM / 演出詳細** は、名称と役割を **基本演出ページ** に寄せる
- 今後 BGM は大きく増える前提で設計する
- そのため、**BGM編集画面ではお気に入りしたものだけを表示する方向を基本** とする
- その旨を UI 上で明記する

### 2-5. 作者ページ / マイページ
- 公開面 = `/authors/[authorId]`
- 本人面 = `/mypage`
- 完全統合ではなく、土台共通化 + 公開面 / 本人面 分離
- `/mypage` は活動ハブ
- 新規作品作成の主導線は `/write`

### 2-6. 反応機能の正式整理
- **ブックマーク** = 保存
- **いいね** = 軽い反応 / 人気度の簡易指標
- レビュー = 言葉の反応
- それぞれ別機能として育てる
- 旧名称の「応援」は **いいね** に置き換える
- 旧名称の「お気に入り」は、作品保存機能としては **ブックマーク** に置き換える
- ランキングやおすすめ作品を表示する時は、**いいね数** を表示対象に含める
- ただし BGM の「お気に入り」は、BGM素材の個人用 favorite として別物扱いにする

対象演出として想定しているもの:

- 場面転換にてBGM変更

- 文字振動
- 文字動作（キーボード打ち込み、フェードアウト等）
- 文字フォント変更
- 文字色変え
- 太字
- 文字斜線
- 文字点強調
- 文字線強調
- 背景変更（紙調、ガラス調、プラスチック調、石調、木材調）
- 挿絵

補足:

- 設定だけでなく **演出付き本文のプレビュー** が必要

## 5. 演出仕様の固定要望

### 5-1. 演出編集ページの具体仕様
- ページ上部あたりに、そのエピソード本文を表示する
- 文字指定演出では
  - 左クリック / 長押しで青線を引いて対象文字を指定
  - リアルタイムで対象文字列として扱う
- 配置が必要なもの
  - 場面転換
  - 背景
  - 挿絵
  などは、**指定行数** により場所を指定
- 行数表示が必要
- 表示予定本文とプレビューは同じ位置に置く
  - デフォルトは本文
  - ボタン1つでプレビューに切替
  - プレビューは仮保存も表示

### 5-2. 演出編集の仮保存ルール
- 背景、既定文字は頻繁に触らない
- 文字演出、挿絵、場面転換などは繰り返し編集しやすくしたい
- そのため、各エフェクト設定に **そのエフェクト単位の仮保存ボタン** を設ける
- 現在どの演出がかかっているかは別の場所に箇条書きで管理
- その一覧には
  - 保存済み / 仮保存
  - クリック時に、どこを演出したものかプレビュー表示
  を持たせる

### 5-3. 背景仕様
- 背景は **紙をメイン** に扱う
- 様々な紙素材を用意し、設定した背景を指定行数分つないでいく形を想定
- 背景色は運営側で変更できるようにする
- 色指定はパレット形式 + 最後尾の虹色から詳細カラー指定

### 5-4. フォント / 色仕様
- フォントも背景同様に色指定可能
- 背景色指定とは別管理
- フォント変更は、使えるフォント素材を集めて一覧から選ぶ方向

### 5-5. 文字演出仕様
- 文字指定は青線で選択した対象文字列ベース
- 種類:
  - 振動
  - 表示
  - その他追加予定
- 変更対象:
  - フォント変更
  - 色変更
  - 太字
  - 斜線
  - 点強調
  - 線強調
  - その他見た目変更
- 振動:
  - 震え方のプリセット
  - 速さ
  - 強さ
- 表示:
  - 一文字ずつ表示
  - すぐ表示
  - フェードイン
  - 書き順に沿って一パーツずつ表示
  - フェードアウトで非表示
  - 表示速度

### 5-6. 挿絵仕様
- 画像をドラッグして保存する場所
- 大きさ指定
- キャプション
- 配置
- 配置は指定行数などで細かく置く前提

### 5-7. BGM場面転換仕様
- エピソード単体BGMと統合して扱う
- 1話通しで同一BGMなら、そのBGMだけ指定
- 転換がある場合:
  - 転換位置
  - 転換後BGM
  - 転換時の切り方
  - 転換時の入り方
  を指定
- 演出編集ページで強弱が必要な設定は、演出基本ページのデフォルトを参照する

### 5-8. 合成音声自動朗読機能
- 朗読許可のある作品に、自動で合成音声朗読を付ける機能を将来追加予定
- 初期は TTS
- クラファン後は voicepark の利用を想定

## 7. 親チャット / 子チャット運用ルール

### 7-1. 子チャット作業の前提
- 子チャットの役割は **VS Code の local ファイル変更指示を出すこと**
- 実際に動かすのはユーザー側とする
- 子チャットは「こちらが動かす前提」で話を進めない
- 以後の実装指示は、原則として **local に存在するファイルをどう直すか** を中心に出す

### 7-2. repo 確認と VS Code local のズレ
- 親チャットが repo 確認を行った時、**repo と VS Code local のズレが見つかったら再判定** を出す
- repo 側で進んでいても、local が追いついていなければ、そのまま次作業へは進めない
- 逆に local だけ進んでいて repo に無い場合も、正式受理や次段階移行は保留する

### 7-3. 正式受理と次作業移行の条件
- 親チャットが正式受理する時は、原則として以下を分けて確認する
  - repo 正史
  - VS Code local
  - 同期済みかどうか
- どれかが不足している場合は、必要に応じて **保留 / 差し戻し / 再判定** を出す
- 「push 済み」だけでは不十分で、local 作業前提として成立しているかも確認対象にする

### 7-4. 子チャットへの今後の指示の出し方
- 既存子チャットで十分なら、その子チャット継続を優先する
- 新規子チャットが必要な場合は、単発名ではなく **ある程度汎用性のある担当名** を付ける
- 他チャットへ貼る必要がある長文は、以後 **TypeScript コードブロック形式** で出す

### 7-5. 新規子チャット名の方針
- 単発の作業名に寄せすぎない
- 近い改善を継続投入できる担当名にする
- 画面1枚単位ではなく、責務単位で切る

## 8. ユーザーから来た改善点・指示の扱い

### 8-1. 基本ルール
- 親チャットは、ユーザーから送られた **改善点 / 指示 / 運用変更案** を受けた時、まず **正史へ入れるべき内容かどうか** を判定する
- 正史へ入れるべきと判断した場合は、親チャット本文だけで済ませず、**docs に反映する**
- 一時的な相談、単発の確認、まだ確定していない案は、そのまま正史へ確定反映しない

### 8-2. docs に書くべき内容
次のどれかに当たる場合は、原則として docs 反映対象とする。
- サービスの固定方針が変わる
- 導線や責務分離の基準が変わる
- 用語や名称の正式整理が入る
- 親チャット / 子チャット運用ルールが変わる
- repo / local / 同期ルールが変わる
- 今後の実装優先順位に影響する
- 次の複数作業にまたがって参照される見込みが高い

### 8-3. docs に書かなくてよい内容
- 単発の確認質問
- その場限りの軽い言い換え
- 実装途中の未確定メモ
- すぐに消える前提の一時対応
- 正史ではなく子チャット内の作業メモで十分なもの

### 8-4. 確認が必要な場合の扱い
- 正史に入れる価値は高いが、内容がまだ曖昧で確定できない場合は、親チャットで確認質問を出す
- この場合も、**確認が必要な論点であること自体** は必要に応じて docs に残してよい
- ただし、未確定事項を確定事項のように書かない
- 書く場合は、
  - 確認待ち
  - 暫定
  - 要再判定
  のように状態が分かる形で残す

## 9. GitHub / local 同期ルール

- GitHub にあるだけで local に無い状態は、正史確認には使えても実作業継続前提にはしない
- 次の作業前に必ず local を同期する
- 用語を分ける:
  - repo正史反映済み
  - local反映済み
  - 両方反映済み
- 「反映済み」は原則、GitHub と local の両方が揃った時だけ使う
